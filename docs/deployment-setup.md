# Guided owner-edge deployment

Implemented 2026-10-31. Run `node scripts/deploy.mjs` from the repository to open a private, loopback-only setup page. The wizard has a prepare-only path and a single Deploy action after the user supplies the destination, exact station identity, initial owner credential and DNS metadata. It deploys the single-owner, single-station edge; it does not deploy the separate local commercial Worker, claim physical hardware, switch a live charger or establish commercial service parity. The [plain-language guides](guides/README.md) are served at `/help` without requiring an owner token or an external documentation host.

## Local Docker

The wizard runs Docker against the active context on the setup host. It generates a private `.chargeos-deploy/<name>/` directory with create-only `compose.json`, file-backed secrets, Caddy configuration, `credentials.json` and `START-HERE.txt`. The parent and setup directories must be real, owner-private directories; a symlinked or shared parent is rejected. Each setup gets a random stable installation suffix in the Compose project name, so a matching human-readable name in an older checkout cannot silently replace that project's containers or volume. A name already reserved in this checkout fails before generating fresh credentials.

Owner and station credentials are independently random 288-bit base64url values. The initial owner RFID is stored only in its file, with pseudonymization handled by the existing gateway. Secret files are mode 0444 inside mode-0700 directories to support the non-root container's read-only mounts; credential receipts are mode 0600. Both Git and Docker build context exclude the entire generated directory. The generated Compose retains the current pinned Caddy image, separate HTTPS/WSS names, internal-only chargeOS network, unpublished application ports, read-only roots, non-root application image and persistent evidence volume. AI egress still uses the fixed internal Caddy relay.

The wizard uses a verified immutable image when supplied, otherwise builds the checked-out source locally. It invokes Docker through argument arrays, never a shell, and does not put credentials on the command line. `up --detach --build --wait --wait-timeout 180` is bounded by a ten-minute child-process timeout; failures retain all files and data. A container start is not a successful DNS/ACME, charger, migration, financial or Freedom Test result. Resume and stop commands refer to the exact saved file; the wizard never calls `down --volumes` or auto-cleans an uncertain deployment.

## Managed Coolify Cloud

The managed adapter requires an existing account and connected server, its project/environment/destination IDs, a published verified image accessible to the server, and a trusted GitHub repository containing `compose.coolify.json` at an explicitly reviewed 40-character commit. A private repository additionally requires an already connected Coolify GitHub App ID; making this repository public is a separate owner action. This path assumes Coolify's standard Traefik proxy, external `coolify` network, HTTPS entrypoint and `letsencrypt` resolver. It does not purchase hosting or register DNS.

The adapter deliberately uses a **Git-based Raw Compose Application**, not Coolify's ordinary Service parser. Adversarial source review found that the ordinary parser broadens service network memberships. Raw mode preserves the template's explicit network topology: only Caddy joins the external proxy network; chargeOS joins only its private internal network. The template supplies its own unique Traefik router/service labels for console port 8080 and OCPP port 8081. Public TLS belongs to the platform; Caddy retains owner security headers and bounded OCPP proxying. The additional proxy means forwarded-header trust stays off; failure-rate limiting is coarser and based on the immediate peer.

The API sequence is create application with raw mode, pinned commit, no immediate/automatic/preview deployment and no domain override; read back raw mode, build pack, template path and pinned commit; upload runtime-only, literal, shown-once private bootstrap variables; queue deployment. A one-shot, non-root credentials container receives bootstrap variables, has no network, and writes flushed, create-only mode-0444 files to a dedicated volume. Retries verify exact prior bytes and mode and refuse replacement. The main application mounts that volume read-only at `/run/secrets`; its declared environment contains only file paths. A separate isolated initializer writes the Caddy configuration to a different volume, so the proxy never mounts station credentials. Both initializers use the same pinned application image, read-only roots and no ambient capabilities. Coolify and its authorized operators hold bootstrap credentials in private application state and the exited initializer environment; these are not an encrypted external secret-manager claim. No AI key or Coolify API token enters those containers.

Each completed API stage gets a new owner-private receipt. No cloud API token is saved. A failed or timed-out create is never retried automatically; an accepted-but-unreadable or partially configured application must be inspected using the saved receipt before retry. The UI distinguishes prepared, containers-started and submitted. A submitted result proves only an API acknowledgement. No real Coolify account or public DNS deployment has been exercised in this change; the adapter is contract-tested with mocks and the raw template is tested in disposable Docker. Actual platform topology, TLS, persistence and owner recovery remain a hosted launch gate.

## Setup trust boundary

The tool binds only `127.0.0.1` on a random port. Its 256-bit setup nonce is passed in a browser fragment, removed from the address bar, kept in memory and required in a custom header for POST. Exact Host and Origin checks protect against foreign pages and DNS rebinding. No cross-origin access is enabled. The POST uses a closed schema, bounded fields, an 8 KiB body cap, a ten-second upload inactivity timeout and one active operation. The page has a same-origin CSP and no third-party scripts. Cloud calls require an explicitly selected trusted HTTPS origin and refuse redirects; provider errors are not reflected. Stop the tool when finished; the nonce is valid only for that process. Credential values are not returned in the wizard response or rendered result.

The AI helper's 45-second limit applies to provider work after reading the authenticated body; the existing owner API upload timeout remains separate. See [AI troubleshooting](ai-troubleshooting.md).
