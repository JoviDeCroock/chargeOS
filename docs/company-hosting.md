# Native company HTTPS hosting

The separate `Dockerfile.company` and canonical `compose.company.json` provide a guided **synthetic pilot** for the native account/reimbursement service. They do not replace the owner-edge deployment or prove production readiness. The separate `compose.company.coolify.json` adds an isolated managed-company wizard and synthetic Traefik runtime proof. The [reviewed public handoff](public-company-recovery.md) now has synthetic owned-Docker proof through source retirement, fresh HTTPS MFA/mail and a later backup into new quarantine. Live managed-platform/provider/mailbox/customer acceptance, managed recovery transfer and retention operations remain release gates. No public infrastructure is provisioned by the runtime verification command.

## Owned Docker deployment contract

Use a dedicated Docker host/public entrance for this profile: one exact DNS HTTPS origin, no additional reverse proxy/CDN/load balancer, ports 80/443 available, approved exact work email domains, and authenticated certificate-verified SMTP. The account and mail processes share Caddy's network namespace through `network_mode: service:proxy`. Node listens only on 127.0.0.1:9091; it has no published port or independent Docker network. Caddy listens non-root on 8080/8443, published as 80/443. Its explicit redirect always uses canonical HTTPS 443. All three services run UID/GID 1000, read-only, with all capabilities dropped and no-new-privileges. Separate named volumes hold company SQLite and Caddy state. The accounts process has bounded 512 MiB private temporary scratch for the supported 64 MiB recovery database, encrypted envelope and consistent-copy validation; the mailer has 32 MiB.

The production configuration requires a non-root Linux Docker runtime, one file-only auth secret, exact canonical HTTPS DNS origin, explicit SMTP and one to 20 unique approved signup domains. The native builder grants a symbol capability unavailable to ordinary Worker bindings. Worker/D1 and native local-development configuration remain loopback-only. Company roles never authenticate owner APIs or establish physical ownership.

Caddy overwrites exact Host, HTTPS protocol and a dedicated actual-peer IP header. The Node bridge requires loopback socket origin, exact Host/protocol and one syntactically valid IP, discards all caller forwarding headers and supplies only that trusted identity to auth rate limits. It exposes only `/service`, `/help`, selected static assets and the separate account API. Owner, observation, preview and recovery-enrollment routes are unavailable. Caddy refuses request bodies over 512 KiB. The bridge buffers at most each route's body ceiling (32 KiB, or 512 KiB for statement imports), discards rather than buffers any excess up to 512 KiB before refusing, and caps concurrent connections at 512. HTTPS responses carry Secure scoped host-only HttpOnly session cookies, CSP, HSTS and no-referrer headers.

Access logging is off and the proxy's default logger discards output: reset/verification tokens occur in both query and path, including failed-upstream requests. Do not enable request/error logging or add an upstream log collector that records URLs/cookies. Runtime verification checks stopped-backend failures for token absence. Service diagnostics use closed failures/counts; private state must never be pasted into support tickets.

## Guided Docker deployment

Run `node scripts/deploy.mjs` and select **set up company accounts instead**. The private company form asks for one hostname, approved work email domains, contact email and required-TLS SMTP settings. One explicit **Deploy company accounts** action validates the local Docker destination, proves actual read-only bind-file visibility using the pinned Node base, reserves a new private package and starts all three services. Prepare-only checks local context metadata and saves files without launching a container or sending mail. Both paths refuse SSH/TCP contexts and `DOCKER_HOST` overrides; a remote transfer adapter is not implemented. Setup must run on the same Linux host or macOS Docker Desktop computer whose filesystem Docker shares.

The Docker input schema admits no owner, raw service-key or cloud-token fields; the separate managed target has a closed cloud schema. The tool creates a cryptographically random auth key and mode-0444 SMTP/key files in a mode-0700 secrets directory, plus a mode-0444 nonsecret Caddy file for its non-root read-only mount and mode-0600 setup receipt, Compose file and START-HERE.txt. Compose and HTTP receipts contain no secret values; username/password fields are cleared before awaiting the request. Templates are derived from the same canonical JSON model; the existing YAML entrypoint includes it rather than duplicating configuration. The optional manual YAML wrapper needs [Compose 2.20.3 or later](https://docs.docker.com/compose/how-tos/multiple-compose-files/include/); the generated package is standalone JSON.

Each package gets a random stable project suffix and separate local build tags. Startup explicitly pins the verified context and generated project and strips inherited `COMPOSE_*` controls; saved resume/status/stop commands also pin the project. No automatic cleanup, data deletion or retry follows an uncertain start. The owner wizard retains its separate flow, while sharing destination/probe/project protection for Docker starts. The nonce, Host/Origin, body and lifecycle boundary remains in [guided deployment](deployment-setup.md).

## Prepare a disposable pilot manually

From the source checkout, an administrator creates a private 0700 directory outside the repository and shared drives. Put a fresh cryptographically random auth secret of at least 32 characters in `auth` and a filled SMTP JSON file in `smtp.json`. Use the [SMTP template and schema](commercial-service.md#native-smtp-account-delivery); do not use inline secrets, insecure TLS or disabled certificate checks. For this Compose profile, each mounted secret file is 0444 inside the 0700 parent so non-root container UID 1000 can read it. Host use outside Docker still requires 0600. The reader accepts shared modes only for an actual deepest read-only mount under canonical `/run/secrets`, with no symlink/hardlink. Protect the host parent; it contains the secret files.

Set nonsecret `COMPANY_DOMAIN`, `COMPANY_ACME_EMAIL` and comma-separated `COMPANY_SIGNUP_DOMAINS`. Set `COMPANY_AUTH_FILE` and `COMPANY_SMTP_FILE` to those absolute private file paths. DNS must point to this host. Do not put a protocol, path, wildcard, spaces or credentials in a domain value.

Run `docker compose -f compose.company.yaml config --quiet`, then `docker compose -f compose.company.yaml up --build --detach --wait`. Inspect `docker compose -f compose.company.yaml ps`; open `https://` followed by the configured domain and create a synthetic approved-domain account. Verify its actual mailbox link and sign in. The mailer sends only newly admitted future SMTP rows. The profile currently supports the system certificate store; private-CA SMTP needs an explicitly reviewed read-only CA secret mount and matching `caFile`, rather than a verification bypass.

Stop using `docker compose -f compose.company.yaml stop`; retain the volumes. Drain the mailer and account process before recovery commands. Never use `down --volumes` for retained company data. Replacing the proxy container also replaces the shared network namespace; stop/recreate the entire profile together. Do not restart only Node against a stale/different proxy topology. The plaintext SQLite volume and separately held secrets need host access controls and encrypted storage/backups appropriate to the operator.

The mail worker publishes a private volatile heartbeat only after a queue pass finishes. Its Docker health check requires a live process and a marker no older than one minute; the file contains only a PID, is create-only/private and is removed only if its inode still belongs to that worker. It is neither mailbox-delivery proof nor recovery authority. Account and mail containers receive a 90-second stop grace period so their bounded requests and SMTP drain can finish before Docker resorts to a forced stop.

## Admission and recovery

Exact approved domains constrain signup and invitations. New signup reserves a real five-minute, unclaimable SMTP slot and recipient/global send admission before password work. The same request's opaque capability completes the row; unused reservations are removed, and crashed ones expire without delivery. Invitations, mail and audit commit atomically. There are at most 1000 pending SMTP rows, 20 admitted messages/minute, one message per kind/recipient/minute and 10 signup admissions/minute. Ordinary reset responses remain non-enumerating; a suppressed later resend is not an inbox-delivery guarantee.

The public bridge allows 120 requests/peer/minute and 1200 globally/minute. New peer admission stops at 4096 existing rate rows; bounded stale cleanup removes at most 100 expired 60-second counters/request, including Better Auth's windows of at most 60 seconds. The global bound also limits auth-created counters during concurrent requests. These are application bounds, not volumetric public-edge protection or long-term business-data retention. Peer keys are hashes; recipient keys use a secret-keyed HMAC rather than storing email addresses in rate keys.

Encrypted backups can retain an exact public source origin as metadata without granting runtime authority. Every restore generates a fresh local HTTP configuration and secret, clears sessions/passwords/MFA/verification/invitations/queue/rate state, and enters SQLite quarantine. Existing local reconciliation, fresh enrollment and atomic reviewed release remain required. A reviewed local release is cryptographically bound to its original local address; the native server, mail worker, backup and checkpoint refuse another origin even with the same database and secret. No direct copy/import shortcut is provided: use the separate [reviewed public handoff](public-company-recovery.md), whose source retirement and exact-origin install are verified independently. Managed-cloud recovery is not implemented. The original live source must be fenced during real recovery; hashes and synthetic tests cannot establish current HR/finance truth.

## Managed company deployment

The same company form supports **Managed through Coolify** without a local Docker dependency. This is a fresh-install adapter for standalone Docker with Traefik, its `https` entrypoint and `letsencrypt` resolver. It requires an existing connected server/project/environment, trusted Coolify HTTPS API/token, accessible published company runtime and proxy image digests, and the trusted GitHub repository/branch plus exact reviewed commit containing `/compose.company.coolify.json`. Private repositories need a connected GitHub App. Both images and the template must come from that reviewed source. No official published company image is implied: the operator builds, verifies and publishes their own. Hosting, DNS, registry access, certificate issuance and mail-provider access are prerequisites.

The adapter writes a private intent receipt before network mutations. It checks the server is standalone Traefik without Cloudflare Tunnel/traffic analytics, creates a **new** destination with a unique network and reads back its exact network/server/type. It then creates the pinned Git Raw Compose application with automatic/preview/instant deploy and shared-network attachment disabled. Raw settings, revision, template path, environment redaction and the application's single primary destination are read back before any company auth/SMTP credential is sent. Only then are literal, runtime-only, shown-once bootstrap variables uploaded and deployment queued. API redirects, oversized/unreadable responses and unsupported API capabilities fail closed; no mutation retries or automatic deletion occur. Inspect the private stage receipts and existing resources after uncertainty. Managed prepare-only packages are review/export artifacts, not resumable deployments. Only after an explicit prepared result and no cloud-intent.json may the reviewed settings be submitted through the wizard under a new name; preserve the review package. Destination creation may succeed even if proxy attachment failed; **submitted is API acknowledgement, never readiness**.

Only company Caddy joins the dedicated external destination network; no service joins the shared `coolify` bridge and no host port is published. The platform proxy must be its only other network member. Traefik terminates TLS; explicit HTTPS-only labels route the exact host to Caddy 8080, which overwrites protocol/Host and derives identity from the actual platform peer. Accounts and mail share Caddy's namespace; Node 9091 remains loopback-only. A network-free one-shot initializer writes separate auth and SMTP volumes. Accounts mount only auth at `/run/secrets/auth`; mailer also mounts SMTP at `/run/secrets/smtp`, both read-only. Caddy receives neither. All company containers are UID 1000, read-only and capability-free. Never add another workload/destination, HTTP account router, extra proxy/CDN or alternate proxy type. Trusted Docker/platform administrators remain in the host custody boundary.

The normal account server also retains a private process lease in company data until HTTP work drains and SQLite closes. Planned service stops remove it; a crash or host interruption may leave it and require a stopped-process audit before restart. Do not delete uncertain custody or deploy the same database under a new name. SMTP and online coherent backup/checkpoint operations remain separate and can coexist with the normal lease.

The operator must keep **platform and Caddy access/request/error URL logs, traffic analytics and URL-recording collectors disabled**. The wizard requires explicit operator confirmation; the app cannot enforce the platform's logging configuration. Rate identity is the platform proxy, so sign-up/sign-in share the existing five attempts/minute and reset shares three/minute across users. This is a small synthetic pilot, not fleet capacity or public launch readiness. Do not enable untrusted forwarded IP headers to increase capacity.

For every actual platform installation, verify HTTPS without certificate overrides, inspect deployed labels and actual network membership, confirm numeric-IP sibling isolation, exercise synthetic signup/verification/login and a restart with retained records, and check failed verification/reset URLs are absent from platform/application logs. The synthetic drill below does not prove a real platform's settings. Use the separate owned-Docker reviewed handoff for public recovery; this managed adapter still creates fresh installations only.

### Operator image preparation

On the reviewed source checkout, use your registry and commit-specific tags. Build the `runtime` and `proxy` targets in `Dockerfile.company`, run `pnpm verify`, `pnpm verify:company-runtime` and `pnpm verify:company-managed-runtime`, and publish only the reviewed images. Resolve both registry digests and provide their full `repository@sha256:…` references with the matching Git commit to the person running setup. Use the same supported CPU architecture as the connected server. Never substitute `latest`, the owner-edge image, an unreviewed template or a local-only image tag. Registry credentials belong to the server operator, not the setup form. Company image publication is operator-managed; it is not part of the owner-edge signed release workflow.

Primary Coolify references checked 2026-11-01: [create a server destination](https://coolify.io/docs/api/endpoints/destinations/create-server-destination), [destination readback](https://coolify.io/docs/api/endpoints/destinations/get-destination-by-uuid), [server readback](https://coolify.io/docs/api/endpoints/servers/get-server-by-uuid), [Raw Compose](https://coolify.io/docs/applications/builds/docker-compose), [destination lifecycle source](https://github.com/coollabsio/coolify/blob/main/app/Models/StandaloneDocker.php). These APIs and actual source behavior are required; older versions without them are unsupported rather than silently falling back to a shared network.

## Verification

The native image also contains an internal fresh-volume credential initializer for the managed adapter. It accepts a bounded generated key and verified-TLS SMTP settings, writes a private volume with flushed create-only read-only files, and permits only byte-identical restarts. Changed keys/settings, unsafe links/modes and stale initialization custody refuse. It never rotates credentials or opens recovered data. Its closed logs contain no settings. Platform administrators can still read bootstrap credentials retained in Docker/Coolify configuration; deleting the process environment is not platform erasure. This primitive alone is not a managed deployment or readiness result.

`pnpm verify:company-runtime` generates the actual wizard package and builds both pinned images and uses disposable loopback-only host ports plus a synthetic internal CA. It calls the real Docker runner with a conflicting inherited project name and proves an existing sentinel container/volume stays untouched. A private synthetic SMTP server checks generated settings, required STARTTLS and actual verification mail without external delivery. It also checks the resolved topology, actual HTTPS verification/login and Secure cookies, rejected foreign signup, owner/enrollment exclusion, another container's inability to reach 9091, canonical redirects, secret-free stopped-upstream logs, read-only mount negatives and compiled checkpoint/export/local-quarantine restore of a database above 60 MiB. It deletes only its own temporary containers/volumes. No external SMTP is attempted; `pnpm verify:service-mail-runtime` separately exercises compiled TLS delivery against the synthetic SMTP fixture. Native tests cover admission races, bounds and public-origin quarantined restore. Run the ordinary `pnpm verify` and owner `pnpm verify:runtime` gates as well.

`pnpm verify:company-managed-runtime` exercises the actual generated managed model through pinned Traefik with its Docker provider and a synthetic trusted certificate in place of ACME. It checks actual dedicated network membership, numeric-IP sibling rejection at 8080/9091, no direct backend access even from ingress, separate auth/SMTP mounts, non-root no-network bootstrap and exact restart/mismatch refusal, verified STARTTLS mail, Secure login and retained sessions after restart, excluded owner/recovery routes and token-free platform/Caddy/application errors. The platform fixture has URL/error logging disabled as required. No real Coolify API account, DNS, public certificate or external mail provider is used.

Primary references checked 2026-11-01: [Better Auth cookies](https://better-auth.com/docs/concepts/cookies), [Better Auth options](https://better-auth.com/docs/reference/options), [Caddy reverse proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy). The single-namespace topology and admission limits above are chargeOS design decisions.
