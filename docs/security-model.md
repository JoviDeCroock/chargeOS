# Security model

## Assets and trust boundaries

Protect owner authority, charging availability, station credentials, RFID identities, meter/session evidence, electrical limits, firmware provenance, personal data, and continuity exports. The vehicle/EVSE safety controller remains outside the chargeOS trust boundary; chargeOS must never bypass its protections.

## Principal model

- **Owner:** immutable root, ownership transfer only through an explicit recovery ceremony.
- **Household member:** selected stations/tags, no ownership or endpoint changes.
- **Employer:** read/export only the sessions needed for reimbursement, with time/site scope.
- **Installer:** expiring diagnostics/configuration capability, dangerous operations require owner confirmation.
- **Energy provider:** bounded schedule/current commands within owner limits; no authorization, firmware, identity, or ownership access.
- **Operator/support:** audited break-glass access, disabled by default for self-hosted deployments.

The Genesis implementation exposes only the safe read subset of these future roles: installers can read station status, diagnostics, the redacted migration dossier, and unreviewed Freedom Test evidence; employers can read tag-free session records; energy providers can read station status. Configuration, scheduling/current control, reimbursement assertions, and charger commands remain unimplemented rather than being implied by a broad role. Fleet mode is one owner security domain: the owner token is root for every configured station. It is not an account or tenant boundary. Two company-gateway roles extend this: a `driver` (employee) may read their own charger and manage personal cards on it, and `finance` may read a monthly business-session feed. Both are delegate capabilities under the owner root, not accounts. Marking a charger company- or employee-owned is a planning label; it never moves the software root, and an employee-owned charger on a company gateway is controlled by whoever holds that gateway's owner token.

## Commercial account boundary

The separate local `/service` uses Better Auth password/session, verification, recovery and authenticator/backup-code flows with Worker/D1 or native Node/SQLite records. HttpOnly SameSite cookies are scoped to `/service/api`; the owner API still requires its independent bearer credential. Every organization route resolves explicit membership; privileged mutations recheck administration inside atomic statements. Invitation acceptance is verified-email-bound, expiring and one-use; removal ends membership access without changing physical owner credentials. No station claim or charger-control capability is implemented.

Worker and ordinary native local configuration accept only configured loopback development. A separate [native company HTTPS Docker pilot](company-hosting.md) adds symbol-gated public configuration through a sole loopback proxy, exact signup domains, Secure cookies and bounded mail/rate admission. Fresh company setup has separate owned-Docker and isolated Coolify guided pilots. The [reviewed public recovery handoff](public-company-recovery.md) has synthetic owned-Docker proof; live platform/customer acceptance and managed recovery remain gated. Local operator-outbox links are secret development material and do not prove real mailbox ownership. They are absent from application APIs and audits; trusted local Wrangler tooling/database access or the native recipient-scoped outbox command can read them. Native configuration/database files require private permissions and reject final symlinks and hardlinks. Its HTTP bridge binds only IPv4 loopback, checks Host/Origin, bounds bodies, preserves separate cookies and ignores caller proxy IPs for rate limiting. Atomic SQLite batches cannot interleave asynchronous work and migration hashes must match the checked-in source. SQLite is not encrypted by this implementation, and live mail-provider/customer acceptance and operational retention remain required. Restoring stale commercial state can revive revoked sessions, used recovery codes or links and roll back membership/financial decisions; owner-edge continuity does not recover this database. See [Commercial service](commercial-service.md) and [ADR 0003](decisions/0003-separate-commercial-worker.md). These controls do not establish station tenancy, commercial disaster recovery or externally anchored audit integrity.

The native commercial backup encrypts a validated consistent SQLite snapshot with fixed, bounded scrypt/AES-GCM parameters and an authenticated commercial format/version/time boundary. Its original database credential records remain owner-secret encrypted backup content; the old service auth secret is omitted. Restore deletes password/OAuth accounts, sessions, authenticators/backup codes, verification/reset/outbox state and pending invitations, resets verification/MFA flags, and generates a new auth secret. Secure deletion/vacuum removes old credential cells from the restored copy. A database-resident marker quarantines all restored snapshot memberships and finances; normal native constructors refuse an unreleased marker even when its row is absent or the file is moved. Only explicit operator inspection may open that unreleased state. Current identity/roster and post-snapshot financial reconciliation, fresh credential enrollment and the guarded local finalizer below are required before release. There is no bypass switch; production recovery remains unproven. Exact schema checks reject extra triggers/views before sanitization; create-only private output and inode-guarded cleanup preserve existing/replaced targets. See [Commercial recovery](commercial-service.md#encrypted-native-backup-and-quarantined-restore).

Recovery review preparation binds the full quarantine provenance and immutable identity/business state to complete current roster/eligibility decisions and a matching original-source financial checkpoint. It consumes private, bounded evidence files and retains only their digests in the private report. Current creator protection, complete organization/member coverage, immutable end conflicts, freshness and foreign-restore checks fail closed. Source retirement and external identity/financial truth remain operator attestations; local email links and evidence hashes prove neither. Lifecycle custody excludes concurrent official recovery operations, refuses stale locks and preserves replacement directories. No review command mutates business/authentication state or enables startup. Its artifact must be revalidated before future enrollment/final release; it has no charger or payment authority.

The separate native enrollment listener permits only kept, exact reviewed identities to consume fresh random links and set a new password/TOTP. Tokens are durably consumed before hashing, progress updates are serialized/HMAC-authenticated, and actual credential/seed/code fingerprints must match before readiness. A database/file crash mismatch requires reissue; flags alone never imply readiness. Recovery cookies have an independent prefix; pre-session MFA challenges bind user/epoch/nonce/review to the exact signed factor cookie, and duplicate recovery cookies are refused before auth side effects. Signup, reset requests, identity edits, MFA disable, backup-code login, remembered devices and business/owner APIs are absent. Direct authentication API calls have explicit limits of five requests per minute for each endpoint and a broad cap of 60 requests per minute for the trusted peer. Current review/evidence bindings are rechecked before actions. Shared HTTP shutdown waits for handler promises after socket aborts, retaining SQLite/custody until completion. The private state authenticates contents, not rollback or cloned packages, and grants no release authority. All links/configuration remain local operator custody; activation is not proof of real mailbox ownership. See [Enrollment](commercial-service.md#fresh-recovery-credential-enrollment).

The native local recovery finalizer requires a still-current actual review and every kept user's real ready proof. Before mutation it validates the deterministic cutover on a consistent private copy. Full-state and required-row guards execute under `BEGIN IMMEDIATE`; roster, eligibility, cleared auth sessions and release authority commit together. Recovery-generated rows identify an operator release rather than impersonating a member. Startup/outbox require exact Q/history/active schemas, same-restore provenance, the current-secret receipt HMAC and unchanged prior history; partial markers never enable access. A committed receipt remains usable after review expiry and ordinary state changes. Later encrypted restore retains historical attribution but strips active release authority and creates new quarantine/credentials. Historical HMACs are not verified with a lost source secret; authenticated backup encryption and current review provide the fresh-host boundary. The local release receipt alone proves no source fencing, external identity/finance truth, rollback resistance or safe cloned instances. [Local reopening](commercial-service.md#reopen-a-reviewed-local-recovery) describes operator custody and version restrictions.

The separate public handoff requires the original unexpired review/evidence and fresh credential proofs, stopped-service custody and complete finished-copy schema/finance/size checks before source retirement. Its atomic source transaction deletes active release authority and seals an authenticated retirement receipt. Only a matching public-install receipt with that retirement, current key, retained history and exact HTTPS origin extends the reviewed local release. The durable candidate is the capsule database; create-only output and signed inode-bound installation journals permit only exact interrupted publication retries. Source/configuration/evidence/capsule/settings paths are rejected inside software build contexts; prepared starts allow only external private folders or the actual ignored generated subtree. Every later restore strips active public authority, rotates credentials and returns to quarantine. Known-source fencing does not establish external retirement, prevent copies held with the key, or resist full-state rollback. See [Public recovery](public-company-recovery.md).

Native SMTP delivery is explicit opt-in for newly queued local-trial account links. Migration/default channel values preserve old developer links as unsendable `local` rows. Queue claims and attempts commit atomically before network I/O; completion requires the same opaque lease. Link kind/origin/callback, recipient and current invitation/verification checks precede fixed text templates. The configured MTA must use authenticated, certificate/hostname-verified implicit TLS or mandatory STARTTLS. There is no insecure override. All transport diagnostics map to closed codes and logs contain aggregate counts only. DNS, SMTP responses and total work are bounded; recovery custody survives the library's early end event until actual socket close and durable queue update. Q blocks dispatch, and restore/reissue/release clear pending/leased mail. SMTP credentials/activation stay outside recovery packages. Ambiguous acceptances may duplicate deliveries; MTA acceptance is not mailbox delivery or production-hosting proof. See [Native mail](commercial-service.md#native-smtp-account-delivery).

## Company support boundary

[Support cases](support-cases.md) use current membership in every SQL read, retry and mutation. Drivers see only their own cases; current finance/admin members see the organization queue. Statement references require the same reporter and tenant. Exact revision/role/assignment guards protect concurrent updates, and only the reporter confirms a current proposed resolution. Messages are bounded plain text, with no attachments, internal staff notes, automatic AI/search disclosure or financial/charger side effects. Durable event/audit history survives offboarding and is replay-validated during native recovery. These are internal consistency checks, not independent signatures or proof of external resolution.

## Commercial reimbursement review

Dated assignments and immutable policies reference organization members and non-secret business aliases; they do not authorize a charger. Server-side import calculation ignores client totals and persists a byte-hashed, minimized snapshot. Driver reads/exports are employee-scoped; finance sees the organization’s business records. A new approval requires a reviewer other than the employee and the draft creator, enabled MFA plus a current TOTP (ten consecutive failed step-up attempts lock it for 15 minutes, and the signed-in library TOTP endpoint is refused after enrollment), the exact snapshot digest, current finance membership, unchanged eligibility and no unresolved rows. Unique organization/station/session reservations, approval and audit commit together. Membership removal atomically closes future business eligibility without touching owner charging. Approved eligibility changes are flagged for correction review. Corrections now append immutable receipts under a unique predecessor gate, require both snapshot hashes and a fresh TOTP from someone other than the employee/draft creator, and retain original-root session reservations even after cancellation. Consistent reads verify snapshots, receipts and journal/head balance agreement before export. No payout or post-settlement reversal is implemented. See [Reimbursement statements](reimbursement-statements.md).

## Primary threats and controls

| Threat                          | Control                                                                                                                                                                                                                 |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Charge-point ID spoofing        | Provisioned allowlist, unique random credential, physical/local claim challenge; never auto-enroll by ID                                                                                                                |
| Backend impersonation/MITM      | WSS TLS 1.2+, valid hostname/certificates, mTLS where device supports it                                                                                                                                                |
| Stolen RFID                     | Tenant-scoped pseudonym, visible last sync, local incident/revocation procedure, unknown tags rejected                                                                                                                  |
| Credential leakage              | Secret manager/encrypted edge store, no logs/exports, rotation path, least privilege                                                                                                                                    |
| Malicious remote start or limit | Owner-only command route (no delegate scope), desired-owner-card-only remote start by pseudonym, active-session-only remote stop, exact confirmations for reset/unlock, no `Inoperative`, audited intent/answer/failure |
| Firmware compromise             | Vendor-signed sources, owner-only approval, recorded version/hash; no opaque support upload                                                                                                                             |
| Meter/reimbursement fraud       | Preserve raw observations and provenance, signed exports, flag clock gaps/duplicates; do not call unverified data fiscal-grade                                                                                          |
| Protocol abuse/DoS              | Strict schemas, 1 MiB OCPP message cap, one socket per provisioned identity, bounded TCP/upstream connections, per-peer token bucket, malformed-message close, owner-API body/auth limits                               |
| Insider/support abuse           | Expiring capabilities, reason/purpose, append-only audit, owner-visible access history                                                                                                                                  |
| Recovery bundle theft           | Authenticated encryption, explicit export, separately held recovery secret; current raw owner tags are recovery authority inside the ciphertext                                                                         |
| Compromised release path        | Tag/package identity check, SHA-pinned actions, exact-digest runtime drill, create-only version tag, GitHub/Sigstore provenance and SBOM attestations                                                                   |

## OCPP profile

For OCPP 1.6J, require WSS plus unique HTTP Basic credentials when the charger supports the OCA security extension. Prefer mutual TLS when interoperable. A lab-only LAN WS endpoint must be isolated, time-bounded, and never described as production-safe. Reject unknown stations before registering handlers.

## Implemented owner-edge controls

- The OCPP and owner API listeners bind to loopback by default and use distinct ports and credentials.
- The production Compose boundary publishes only Caddy on ports 80/443. OCPP and the owner API stay on an internal-only Docker network under separate TLS hostnames. Caddy handles certificate automation and WebSocket upgrade proxying; application authentication remains authoritative.
- Station authentication resolves the identity through the strict registry and compares that station's unique secret in constant time; a CPID alone is insufficient. Unknown and duplicate live identities fail closed.
- The OCPP boundary caps complete WebSocket messages at 1 MiB by default, permits one authenticated connection per provisioned identity, bounds accepted TCP and proxy-upstream connections, pings away dangling peers, closes after three malformed messages, and independently token-buckets every peer's valid supported or unsupported RPC calls. Exceeding the valid-message limit appends one data-free audit event and closes only that peer. Schema-invalid and unrecognized calls consume the same per-peer token bucket. Each strict-schema rejection, in either direction, appends a `ProtocolMessageRejected` audit holding only a standard OCPP 1.6 action name (any other charger-chosen method is recorded as `Unrecognized`), the error code, the first failing schema keyword and JSON path, the origin and the phase. Every OCPP 1.6 schema forbids additional properties, so the path contains schema field names only. Payload values are never copied, so a rejected frame that carried a raw RFID cannot leak it. At most 16 rejections are recorded per connection, and compaction keeps the latest 20.

OCPP 1.6 identifiers are case-insensitive `CiString20` values. Online `Authorize` and `StartTransaction` decisions therefore fold ASCII letter case only (no Unicode folding), and the owner-tag registry refuses a new tag that differs from a desired tag only by case. Revoking a tag also revokes any legacy case variant seeded or restored before that rule, and is refused if it would leave no owner credential. A full local list sends one entry per case-insensitive identifier. Pseudonyms are still derived from the exact reported string, so a card reported in a different case shows a different pseudonym in evidence. BootNotification SIM identifiers (`iccid`, `imsi`) and StatusNotification free text (`info`, `vendorErrorCode`) are stored only as station-keyed 24-hex digests (`…Digest`). They identify a subscriber or may carry a raw card UID, and evidence reaches shareable exports. Projections and redacted exports replace raw values from older ledgers with `[redacted]`. Charger-initiated `DataTransfer` is answered `UnknownVendorId`; evidence keeps only station-keyed HMAC digests of `vendorId` and `messageId` and the fact that data was discarded. `SecurityEventNotification` keeps a whitepaper-defined `type` (any vendor type is recorded as `VendorDefined`) and `timestamp`, and discards free-text `techInfo`. Firmware, diagnostics, signed-firmware and log status notifications keep only their status and request ID.

- The pinned `ocpp-rpc` package has a narrow checked-in patch at its private schema resolver: malformed legacy `urn:<method>` identifiers are normalized to valid `urn:ocpp-rpc:<method>` identifiers. This keeps wire-visible method names unchanged while permitting advisory-fixed AJV and fast-uri releases. The production audit and complete protocol/runtime suites guard that patched dependency boundary.
- Refused upgrades leave only owner-visible, in-memory diagnostics: a closed reason code per attributable charger (wrong/missing password, this charger's own password under another name, duplicate connection, no OCPP 1.6 subprotocol) and a text-free counter for attempts matching no charger name or password. A presented charger name is echoed back only when it carried that charger's own password and is printable ASCII without `/`. Passwords are compared against every station so timing does not reveal which matched; diagnostics never reach evidence, exports, logs, delegate projections or AI context, and status codes are unchanged. Anyone who knows a charger name can overwrite its last-refusal reason, so the console labels it an explanation of the last attempt, not proof of who made it.
- Tap-to-add holds at most one raw card value per station in gateway memory, only while the owner has armed it (two minutes, then five to confirm), never in a projection, response, log or evidence record. A second different tap cancels the offer, so a passer-by's card cannot be added silently; confirmation needs the owner token and the exact pseudonym, and hands the value over once. The tap itself is still refused. A single-station first boot may have an empty desired set; removal can never return to it, a deleted state file cannot be re-seeded empty past the ledger audit, and synchronization and continuity export refuse an empty set.
- An owner may accept one extra charger name (identity alias) per station, only for a name presented with that station's own password in the last 15 minutes. The station's unique password still authenticates every connection under either name, the alias shares that station's single-connection reservation, and the gateway always uses the station resolved during authentication rather than the name in the URL. A ledger record is written before the alias is honoured; names colliding with a configured ID or claimed by two stations are ignored at startup. A charger-point ID alone still proves nothing.
- The OCPP listener refuses an undecodable upgrade path before authentication and contains upgrade-handler failures, so a malformed request cannot terminate the edge. A handshake refused after authentication releases that station's single-connection reservation on socket close. Fleet station secrets must be unique, and continuity decryption requires a 12-byte IV and a full 16-byte GCM tag.
- Owner API routes use a separate bearer token of at least 32 characters, same-origin requests, no cookies, security headers, and a bounded per-address failed-authentication limit. Owner-token failures are not cleared by a successful delegate call. Malformed bearer values never trigger a ledger read, and each delegate grant is limited to 60 requests per minute because every delegate call reads the ledger and appends a use audit. Forwarded client addresses are ignored by default; production enables them only because the application has no host port and Caddy is its sole internal-network peer. Invalid forwarded addresses fall back to the socket peer.
- Single-station secrets retain mutually exclusive inline/file-backed settings. Fleet mode instead requires one owner-private or read-only-mounted `CHARGEOS_STATIONS_FILE` with a closed schema, unique IDs, unique per-station secrets, non-empty owner tags, bounded display metadata, and at most 1,000 stations; mixing it with legacy station settings is rejected. Values are never printed.
- Owner directory names (`directory.json`) are owner-only presentation data: closed schema, mode `0600`, 1 MiB bound, pseudonym-keyed cards, normalized 1–80 character names without control or format characters, and the same atomic write discipline as owner tags. They are never written to the ledger, redacted exports, field packs, delegate projections or AI troubleshooting context, and are not in continuity bundles. A card is nameable only while it is in that station's desired set; revocation deletes its name. An unreadable or unsafe file makes the directory read-only without overwriting it and never blocks charging or owner-tag mutation.
- Each canonical raw owner-tag set is a closed-schema, mode-`0600`, size-bounded file. The primary station retains `owner-tags.json`; additional stations use station-ID-digest filenames under `owner-tags/`. Each station-keyed HMAC detects edits and use with the wrong station secret; startup rejects symlinks, unsafe permissions, malformed state, an empty set, and failed authentication. Writes affect only the selected station and use a unique owner-only temporary file, `fsync`, atomic rename, and directory `fsync`.
- Owner-tag add and revoke routes require the owner bearer token; delegates have no corresponding route. Adds reject whitespace/control ambiguity and duplicates. Revocation addresses only a pseudonym, requires an exact warning phrase, and cannot remove the final owner credential. A mutation changes desired state only, never silently sends `SendLocalList`.
- A successful mutation appends only its pseudonym, state version, count, and state HMAC to the ledger. If append fails, the state file is rolled back. If that rollback also fails, the live desired set follows the durable state and the API reports a restart-required internal failure; startup appends a pseudonym-free reconciliation record before listening. The same reconciliation covers a process death after persistence but before audit. Because persistence precedes audit, state at or below the last audited version is accepted only when it holds exactly the last audited tag set (a continuity restore or interrupted first reconcile), and then continues past that version. Any other rolled-back, first-boot or reseeded state is refused rather than re-desiring revoked tags. RFID values in OCPP payloads and authorization-list commands are HMAC-pseudonymized before persistence.
- Full-list commands and their results retain a monotonic list revision. Reconciliation advances charger-acknowledged RFID state only for an `Accepted` result paired to that revision; legacy results pair only with the nearest unresolved command. The owner console exposes pending additions and stale-access revocations using pseudonyms, never raw RFID.
- The ledger has a configurable 256 MiB default ceiling. Startup verifies the complete chain before binding listeners; each serialized append is size-checked before write, and refusal leaves the previous chain intact. Health degrades before maximum-message headroom is exhausted. No implicit truncation or rotation is allowed.
- Each ledger record is chained to the previous SHA-256 hash and includes a station-keyed source-payload fingerprint. Verification fails on record edits, insertion, removal, or reordering; the latest owner-held bundle acts as an authenticated tail checkpoint.
- Redacted charger-scoped exports omit station/API secrets and raw RFID values. Encrypted continuity bundles read the current canonical desired tags and contain them with the recovery configuration and verified ledger; they use AES-256-GCM with scrypt-derived keys, refuse overwrite on restore, and require a separately stored passphrase. The current encrypted format represents exactly one station, so export fails closed when fleet mode is active instead of emitting an incomplete artifact. Field-grade continuity therefore still uses one station per recoverable edge until a versioned fleet bundle and restore drill exist.
- Continuity rotation authenticates the old bundle and chain, requires a different strong passphrase, uses fresh salt/IV/authentication material, writes a new mode-`0600` file without overwrite, and never restores plaintext credentials to disk. Passphrase files must be owner-private regular non-symlinks and are opened without following a final symlink.
- Continuity payload schema 3 carries the edge's explicit OCPP connection, payload, valid-call, burst, and evidence-capacity limits plus content-addressed archive boundaries. Fresh-path restore reproduces those bounds/segments but forces proxy-header trust off; inspection and the restore manifest disclose archive/current counts, source trust, the forced safe state, and whether legacy defaults were applied. Proxy trust can return only after the replacement deployment independently proves the single-proxy/no-host-port topology.
- Offline archive rollover requires the exact stopped-edge confirmation and a separately held encrypted bundle matching every current event and archive boundary. The next active segment is linked to an atomically renamed owner-only archive by a redacted audit event. Sequence gaps, extra files, changed segment bytes, broken boundary hashes, concurrent/stale evidence, and empty rollovers fail closed. Archived bytes remain on edge and cannot yet be safely deleted.
- Schema-4 compaction is create-only replacement recovery, not in-place retention deletion. It authenticates the full source bundle, requires an exact owner custody confirmation, hashes the exact encrypted source bytes, preserves a typed custody record and explicit carry-forward source hashes, aggregates only projection-safe retry/noise records, reserves append headroom, and writes a new owner-private bundle without overwrite. Custody verification re-authenticates the referenced source, matches its chain metadata, and deterministically compares every carried record before the compacted bundle may be relied on. Restore/install still require a new path and empty volume; the software never removes the full source bundle or old edge. Missing any referenced bundle means full historical evidence is unavailable and must remain visible as such.
- Production continuity export runs the compiled CLI inside the existing non-root container, reads its already-mounted credentials and ledger, accepts one bounded recovery-passphrase line through redirected standard input, and emits only the authenticated encrypted envelope to standard output. The passphrase is never an argument, environment variable, container file, or edge-volume artifact; interactive invocation and multiline/oversized input fail closed.
- Production restore requires fresh distinct DNS names and ACME metadata, creates a non-overwriting owner-private package with read-only Compose secret inputs, and marks proxy topology unvalidated. The compiled non-root installer accepts only a verified capacity-bounded chain, creates and flushes an absent ledger, verifies the installed copy, removes its own partial file on failure, and refuses to merge with or replace existing volume state.
- An owner can generate a non-overwriting Ed25519 key directory, keep the encrypted private key owner-only, and sign the station ID, snapshot timestamp, event count, chain head, checkpoint time, schema, algorithm, and public-key fingerprint. Public verification requires no bundle secret; optional comparison authenticates the matching continuity payload. The signature is not an identity proof or independent timestamp.
- Internal API failures return a generic message. The public health route reveals only service availability.
- Freedom Test mutations require the owner bearer token, accept at most 8 KiB of JSON, validate exact bounded fields, and append to the same integrity-checked ledger. Starting a witnessed run additionally requires an exact confirmation phrase, a matching authorized Boot, and all automatic online proofs. The run is bound to the exact inventory, migration authorization, and Boot events; witnessed writes must name its UUID and fail closed after any baseline change. External photos/videos/documents remain outside chargeOS; the ledger stores only their SHA-256 digest, outcome, observation time, and non-secret run ID.
- Delegate grants require the owner token, accept only canonical roles and role-bounded read scopes, must expire between five minutes and 90 days, and return the high-entropy bearer secret exactly once. Only its SHA-256 verifier and short hint enter the ledger; owner projections and exports remove the verifier. Authentication compares the verifier in constant time, checks expiry and revocation on every request, and exposes no owner mutation route. Successful delegate reads are durably audited before data is returned.
- Console-added chargers live in `managed-stations.json` (closed schema, mode `0600`, regular non-symlinked file, 1 MiB and 1,000-station bounds). Each gets a fresh random 20-byte (40 hex digit) password shown once on its setup sheet; IDs are unique case-insensitively against configured, added and retired chargers and against every station ID in the ledger, so a name with history (evidence, cards or employee links) never attaches to a different charger. The file is persisted before a ledger audit that carries only the action, registry version and a SHA-256 of the whole state, never a password. Startup refuses a missing file when audits exist, an older or differing file, or a file more than one change ahead of the ledger; exactly one change ahead is a crash between the two writes and is reconciled with an audit. A password can be replaced only for an added charger that never connected and has no cards, because card pseudonyms and the owner-tag state authenticator derive from it. Known limit: a crash between committing the new password and rewriting that charger's empty owner-tag file leaves a file authenticated with the old password, and startup then refuses; restore both files from the same backup or retire and re-add the unused charger. Retirement requires a typed per-charger phrase, refuses the first charger (which anchors legacy routes), disconnects the socket and makes the identity unknown to authentication.
- Card classification (`card-policy.json`, mode `0600`, closed schema, 2 MiB bound) stores only charger ID, pseudonym, ownership (`company`/`personal`) and use (`business`/`private`). Only cards currently desired on that charger can be classified; revoked cards are pruned. Each change appends `CardPolicyChanged` with the pseudonym and values. An unreadable file makes classifications read-only and empty rather than blocking startup: employees then cannot add or remove any card (an employee confirmation is refused with `503` before the tap is used, and a classification write that fails after the card was added removes the card again). An employee can never add a charger's first card; the owner adds it, so that removal is always possible. Reports never read the current file for past sessions: the finance feed and the usage report rebuild each card's classification from the ledger (`CardPolicyChanged` sets it; the card's removal from that charger, `OwnerTagDesiredStateChanged` `removed`, ends it) and use the one in force when the session started. Because session times come from the charger clock, a change within 15 minutes of the session errs towards private, and a first classification up to 15 minutes after a session also covers it; an earlier session stays unclassified rather than inheriting a later decision. Removing or reclassifying a card therefore never makes its earlier private sessions reimbursable, and the history survives recovery with the ledger. The file itself, which holds only the current state used for employee rights and console labels, is not in continuity bundles.
- The `driver` role (`driver:read`, `driver:personal-cards`) is issued on one charger and resolved to that charger only. Its projection carries station ID, connectors, card pseudonyms with classification and acknowledgement, up to 50 sessions that started after the oldest still-active employee link on that charger was issued (a renewal keeps history whole; offboarding ends every link, so after a reassignment the new employee never sees the previous one's charging) by pseudonym, and the grant expiry, never names, raw RFID or other chargers. It may arm tap capture on its own charger, but never while an owner-started capture is listening or holding a card (`409 card_capture_busy`), so it cannot claim a card an owner or installer is adding; a capture it did not start is invisible to it, and confirming requires that it started the current listening, which an owner start takes over. A confirmed card is always stored as personal/private. It may remove only cards classified personal, never the last card, with the exact stale-access phrase. It may request the owner's own complete-list synchronization, which runs the same preflight. Every call appends `DelegateCapabilityUsed`. The console issues it for 90 days; the server cap is 90 days for every role.
- The `finance` role (`reimbursement:read`) may be issued only on the first charger and is answered only there. It reads one month in a named time zone: `Accepted` sessions per charger by pseudonym with energy, integrity and classification. Sessions with a card that was `private` at the time are omitted and only counted; sessions without a classification are listed as `unclassified`, never as business. Retired chargers stay in the feed for the months their sessions happened. It carries no names or raw RFID. Renewing issues a new 90-day secret and revokes the previous one.
- The employee page at `/me` receives its link as a URL fragment (`#station=…&token=…`), which browsers do not send to the server, keeps it in tab-scoped session storage and removes it from the address bar. The link is still a bearer secret: anyone who has it acts as that employee until expiry or revocation. Serving employees requires the owner API to be reachable from their devices, which means the production HTTPS boundary; the loopback default serves no one else.
- Migration checkpoint and authorization writes require the owner token. The API accepts canonical checkpoint IDs, bounded outcome values, normalized timestamps, external SHA-256 references, a fixed confirmation phrase, a canonical target manifest, and only isolated-LAN WS or certificate-validated WSS transport classes. It validates the manifest against exact station inventory, configuration path, corresponding dossier evidence hashes, selected transport, and current time, then stores only the canonical target hash. Authorization fails until every pre-switch step passes, expires within 24 hours, is tied to the current prerequisite fingerprint, and becomes stale after any prerequisite change. The software records consent and evidence but does not send endpoint, firmware, electrical, enclosure, or SIM commands.
- The migration-target CLI writes a non-overwriting mode-`0600` canonical JSON artifact with a closed schema. It rejects unknown fields, embedded endpoint credentials/query data, likely credentials in the configuration-path field, station-path mismatches, public/loopback/named plaintext endpoints, transport/safety constant changes, malformed evidence digests, and authorized-hash mismatches. The artifact deliberately contains only custody/evidence hashes, not the underlying credentials or household evidence; structural verification does not attest those external facts.
- Migration-target evidence inputs require exactly one caller-supplied digest or direct file per evidence class. Direct inputs must be non-empty regular non-symlinks, are opened without following the final path component, and are rejected if the opened inode, size, modification/metadata time, or final path changes during streaming SHA-256. File paths and contents never enter the target. Operators must use redacted evidence artifacts rather than raw low-entropy credentials because a published digest can otherwise become a password verifier.
- Owner-continuity preparation requires the owner token and an exact separate confirmation phrase. A complete preflight must show every unsafe required key as explicitly writable before any mutation. A charger that explicitly reports `AllowOfflineTxForUnknownId` as an unknown key does not support Unknown Offline Authorization (OCPP 1.6 section 9.1.1), so that one check passes without a write; a key that is merely missing still blocks. The command allowlist can only enable `LocalAuthListEnabled` and `LocalAuthorizeOffline` or disable `AllowOfflineTxForUnknownId`; commands and results are audited, no RFID synchronization or restart is automatic, and `RebootRequired` blocks readiness until a later authenticated Boot and fresh inspection.
- Exact-device migration identity uses separately evidenced pre-switch vendor/model/firmware inventory, then fails the authorized Boot step unless all three observed OCPP values match exactly. Inventory changes alter the prerequisite fingerprint and invalidate prior endpoint-change authorization; a mismatch is never silently normalized or adopted.
- Field-test reports expose device metadata, step states, evidence references, and the ledger head but remain explicitly unreviewed. They contain no raw RFID, station secret, API token, address, or uploaded household evidence.
- The owner-only schema-1 Genesis plan is a deterministic read projection over migration and Freedom state. It exposes stable action/actor/evidence/safety identifiers and bounded instructions but no secrets, raw RFID, endpoint credential, or new mutation capability. It permits the documented endpoint action only while the exact authorization window is active, stops on failed or stale evidence, and never treats a plan instruction as performed physical work.
- Transaction starts persist their Accepted/Invalid authorization decision. Automatic owner-energy evidence requires Accepted. Exact start/meter/stop retries remain auditable but deduplicate in session projections; a conflicting later stop is surfaced and cannot silently rewrite the first projected meter result.
- The field review pack embeds only the redacted continuity export plus unreviewed migration/Freedom reports. Canonical artifact digests and station/head/count agreement detect mutation or mismatched exports; secret-free verification does not prove author identity, chronology, external evidence truth, recovery capability, or certification.
- CI validates the resolved production Compose and Caddy configurations, boots the non-root image with file-backed secrets, and emits a CycloneDX JSON SBOM for the deployed image.
- Owner-edge Caddy runs as uid/gid `1000:1000` with every capability dropped except `NET_BIND_SERVICE`, which the pinned binary's file capability supplies for ports 80/443. A one-shot `caddy-volumes` step gives that user its certificate volumes, including volumes created root-owned by earlier versions. It runs as root, but without network, on a read-only filesystem, with only `CHOWN`, `DAC_READ_SEARCH` and `FOWNER`, and then exits. Caddy starts only after it succeeds. The deployment validator checks this shape for the production, fleet and managed models. The runtime smoke test checks that the process runs as uid 1000 with only that capability.
- Stable tag publication is a separate least-privilege job. It requires the tag to match `package.json`, rejects any current production dependency advisory, refuses an existing GHCR version, builds only a commit-addressed candidate, runs the full production drill against that exact registry digest, generates a deterministic digest/source/SBOM manifest, creates GitHub/Sigstore provenance plus CycloneDX attestations, and promotes version/commit tags only as the final step. Every third-party action is pinned by full commit SHA and checkout credentials are not persisted. No mutable `latest` tag is emitted.

The image attestation proves which GitHub workflow and source revision produced a digest; it is not an independent rebuild, vulnerability clearance, maintainer identity outside the GitHub trust root, field configuration proof, compatibility result, or Freedom Test. Remaining production work includes volumetric DDoS protection appropriate to each public deployment, automated custody-media lifecycle/retention policy beyond the create-only compacted replacement workflow, an external timestamp/anchor for owner-signed checkpoints, protected/signed source tags and release governance, multi-node failover, and a fully authenticated ownership-transfer ceremony.

## Browser-only observation

The `/observe` tool has no backend endpoint and does not consume an owner token. User-selected files are bounded, parsed as data, held only in browser memory and never uploaded by the tool. Selected operational aliases, source digests, policy inputs and draft decisions are exported only on an explicit download; unselected raw columns are omitted. Source/mapping/policy changes invalidate old results and asynchronous reads cannot revive cleared data. The digest is provenance, not authenticity. Its draft cannot authorize reimbursement, create a financial obligation, mark a payment settled or alter station evidence/configuration. See [Local observation](local-observation.md).

The fleet card send requires a current owner-only review. The review token authenticates the candidate set, card pseudonyms and connection/list evidence. The serialized station preflight checks the reviewed connection and desired list again before sending. Review responses expose counts and closed outcomes, never card values.

## Dangerous operations

Changing an OCPP endpoint, disabling local authorization, lowering essential-use availability, updating firmware, erasing a local list, or transferring ownership requires:

1. current backup and rollback path;
2. explicit owner confirmation naming the effect;
3. authorization separate from charger identity;
4. immutable audit evidence;
5. post-change Freedom Test or a visible uncertified state.

## Privacy and EU duties

RFID, location, household/employer relationships, and charging patterns may be personal data. Minimize collection, HMAC raw tag identifiers with a tenant-specific key, scope employer exports, define retention, and support access/export/deletion. Hosted operations need controller/processor clarity and EU data-location commitments. The Cyber Resilience Act should be treated as a design constraint for commercial distribution: vulnerability intake, secure updates, supported lifetimes, and documented dependencies—not as a last-minute certification task.

Company HTTPS pilot source origins may be retained only as authenticated backup metadata. Restore always emits fresh local configuration, rotated secrets, cleared authentication/delivery state and quarantine. The default Caddy logger is discarded as well as access logging disabled, because account tokens can occur in proxy error paths/queries. The Docker proof exercises actual isolation and read-only secret mount rejection; it does not establish production recovery or external HR/finance truth.
